# 系统特色、注释与重复的审查方法

用于生成前的内容审查，或用户明确要求的源码质量改进。不是在 Word 里“改写代码”的模板，也不是查重规避指南。工程依据见 [依据与登记边界](evidence-and-compliance.md)。

## 1. 先辨认这个系统，而不是先套文件顺序

先读实际入口、核心模块、接口/数据定义、测试和用户提供的说明。在当前任务记录或已有设计资料中回答下面的问题；小项目几句话即可，不强制另建表格或文档：

- **真实场景与对象**：谁在什么场景处理什么数据，产出什么结果？名称不能代替实现证据。
- **实际主链路**：输入校验 → 关键处理/状态变化 → 输出/反馈分别位于哪些文件、函数或类型？不适用的环节不要硬凑。
- **辨识度在哪里**：数据单位/坐标系、业务约束、算法选择、权限/状态边界、异常恢复、特定交互或输出契约中，哪些确实在源码里实现？选择决定本系统行为的部分，不凑固定数量。
- **如何验证**：每项所声称的特色关联源码位置、已有测试或可复现步骤。只有实现未执行，写“已定位、运行未验证”；只有需求没有实现，写“待开发”。
- **共享与自有贡献**：第三方库、合法公共模块、脚手架、同一作者跨项目复用分别是什么？来源、许可或归属不清先核验，不把框架能力说成自研创新。

**完成条件**：读者能从“场景 → 真实实现 → 行为/约束 → 验证证据”理解本系统为何这样工作。只有更换系统名、颜色、类别标签、权重路径或配置，不能自动说明业务逻辑或算法发生创新；如实称为配置/适配差异。技术“首创”“提升X%”需额外对照证据，本 skill 不凭排版认定。

如果找不到可支持的特色，明确缺口和有价值的开发方向；没有开发授权就不替用户加功能。不要通过多写类、换架构、随机改命名或堆术语制造差异。

## 2. 注释按理解风险补，不按百分比补

### 优先审查的地方

- 核心业务模块的职责与上下游关系；当现有命名足够清楚时不加冗长统一文件头。
- 对外接口/非平凡函数的输入输出语义、单位、范围、顺序、可见副作用、相关异常；只写调用者需要知道的条件。
- 代码无法直观说明的业务不变量、阈值来源、坐标变换、并发/事务边界、取消与重试、兼容取舍、容错边界。
- 易被误用的算法步骤、复杂正则或性能取舍。可以解释必要的“做什么”，不机械把每句代码翻译成中文。

### 注释真实性

1. 先确认行为再写。历史设计动机、阈值依据、精度/速度收益不能从函数名臆测；证据不足时记录待确认，不用“为了提高准确率”补空。
2. 注释要与实现、测试一致；参数有类型时不机械重复类型，重点写单位和约束。不得注释声称已做校验/脱敏/重试而实现并没有。
3. 简单访问器、直白赋值和框架要求的声明可以没有解释性注释；不设“每函数必须N行”“注释占20%”“每文件同一段简介”等配额。
4. 不复制大段说明书、许可证模板、作者时间戳横幅或无信息的“初始化/处理数据”注释来增加行数。原有许可证和必要工具指令必须按用途保留，不因重复删除。
5. 用项目已有的语言和注释风格；新说明通常使用清楚的中文，保留准确技术术语。Python 区分普通注释与模块/类/函数 docstring；Java/C#/TS 等沿用各自规范，不把 Python 样式强加给它们。

### 落地与验证

- **仅授权排版**：不动源码，不在 DOCX 中临时加注释；列出关键缺口，不能宣称“注释优化已完成”。如这些缺口阻止用户明确要求的质量目标，集中询问一次是否允许维护源码。
- **已授权维护源码或正在开发该系统**：在真实项目的可恢复版本中修改；读回 diff，检查注释/文档字符串位置不破坏语法、编码或工具指令；至少执行对应语言解析/编译和相关用例，涉及行为的改动补回归。再冻结新源码生成文档。
- 若用户选择独立工作副本，保留补丁/副本并标明文档对应哪个版本；不能只在打印文本中“优化”后冒充原项目。原样本不改。

**审查例子（思考方式，不是让所有系统复制的注释）**：
- 图像裁剪：先查 bbox 是像素还是归一化坐标，是否越界、空裁剪、保存失败由谁处理。若实现只是直接切片，不能给它补上“已确保安全裁剪”的虚假说明。
- 流式监测：查时间戳、状态切换与丢帧处理是否真的存在；没实现重连就不能写“自动恢复”。
- 业务审批：查实际权限、幂等和事务边界，而不是用图像项目的“数据预处理”章节改名套用。

## 3. 把重复分开处理

| 类别 | 判断与处理 | 导出时的要求 |
|---|---|---|
| 同一路径被清单重复列入 | 核验确为同一文件，纠正收集/排序 | 只输出一次，记录去重原因 |
| 不同路径、内容完全相同 | 先核对独立模块、空包文件、复制备份、构建用途 | 默认都保留并标记 DuplicateOf；只有确认非交付副本且获范围授权才排除 |
| import / using / include、声明、许可证、框架签名 | 先按语言与文件作用域理解，这是经常必需的正常重复 | 各文件原样保留，不能跨文件仅留第一次，也不集中搬到文档开头 |
| 合法公共模块、脚手架、框架UI/CRUD、相似测试 | 核对来源与责任；形似不必然需要抽象，共享实现也不必伪装成独有 | 自有实现按范围保留；第三方/生成物按来源规则排除并留依据 |
| 多处维护同一业务知识 | 问它们是否应当共同变化、是否产生维护漂移，再提出抽取/配置化候选 | 只在已授权源码中重构并测试；导出器不能直接删片段 |
| 不同系统只替换名称/常量/模型路径 | 比对实际业务链路和规则，区分配置适配与真实差异 | 如实说明共享与差异，提出尚需开发的工作；不新增伪代码或“创新故事” |

**不要为了减少重复而破坏模块化。** 只有同一职责、同一变化原因且回归可证时才考虑共享抽象；若合并后变成大量模式开关和特殊分支，应重新审视，合理重复可能更好。默认不合并多个文件为“单文件系统”，不删除必要 imports，不做无意义重命名或语法改写。

**未使用导入**与**跨文件重复导入**不是一回事。只有在源码维护授权下，结合静态检查、动态导入/重导出/注册副作用及测试，才能删除真正无用的导入。诸如 Python __future__、插件注册或类型导入不能因计数重复移走。

## 4. 可选的本地机械辅助

当项目较大、跨系统相似性受到质疑或需要复核大量注释时，使用 scripts/review-source.py；小项目可人工完成同样审查，不为一个简单函数制造流程。

- 输入生成器 -ScanOnly 的冻结清单；只读源码，校验逐文件原始哈希、实际导出文本哈希和行映射。
- Python 用 AST/tokenize 分列 imports、普通注释、docstring，并定位“有决策分支但无局部说明”的候选函数。出现注释不代表注释有用，候选也不等于缺陷。
- 只在**分析视图**中排除 imports/注释/docstring，找保留标识符和字面量的相同代码窗口；正式源码不受影响。默认8个有token行只是检测窗口，不是合格阈值。
- --compare-manifest 只比较用户明确提供的项目，不自动搜集机器上的其他源码。相同块只是人工复核线索，框架样板也可能命中；改名或语义近似可能漏检。
- 非 Python 或解析失败的文件明确列 manual-required；逐个补人工审查，不当成“零问题”。不要把多文件汇编 DOCX 当作一个可运行 Python 文件检测。
- 超过 --max-groups 的输出有显式截断标记；示例窗口不是完整重复总量。退出0仅表示检查完成，结果固定为 needs-human-review，不产生查重率、原创度或“质量通过”结论。
- 工具不判断业务特色、不验证注释语义、不自动扫描秘密/许可、不证明全项目范围完整；这些仍须人工核验。报告留本地，不默认接在线查重服务。

## 5. 审查收口

完成前核对：每条特色有定位与证据；关键注释缺口已在授权范围处理或真实列为未完成；重要重复候选已分类并给出保留/改进理由；代码维护有实际验证；正文来自冻结的真实源码；格式验收独立通过。

只在已有任务记录保留必要证据（系统判断、源码位置、重复处置、验证结果、未验证项）。不把审查表、功能介绍或比对报告插进源程序正文；也不强制每个小系统交付一套同形文档。若只完成忠实排版，明确只完成该项。
