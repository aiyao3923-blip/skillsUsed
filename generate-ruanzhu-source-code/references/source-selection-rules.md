# 源码范围与业务链排序

## 范围先于页数

- 默认完整收集当前系统符合条件的自有源码，无3000行/固定页数上限，不首尾截取，不为了突出特色而隐去公共但属于项目的实现。
- 优先依据真实项目与版本，不从历史DOCX猜造源文件边界。自动扫描的扩展名/目录过滤只是收集起点，**不能单凭扫描结果证明全项目覆盖**。
- 对照目录与构建/入口依赖核定清单：后端、前端、桌面/移动端、算法、数据库、配置、测试中哪些属于本系统？检查未识别扩展名（例如自有DSL、UI定义）、误被命名过滤的业务模块和扫描排除目录。遗漏须先解决，再作完整性声明。
- 同路径多次列入只收一次；不同路径即使内容相同也默认保留，记录DuplicateOf用于人工判断，空文件列入清单但不制造源码行。

## 排除与敏感内容

通常不收：版本控制/IDE元数据、第三方依赖与vendor、虚拟环境、构建/缓存/覆盖率产物、minified/source map/lock、生成代码、媒体/模型权重/数据库等二进制、凭据/证书/私钥/.env和真实个人信息。自有配置、业务数据定义和有意义的测试属于源码时可收，不能因为“看起来模板化”就删。

- 判断依据为文件职责和来源，而不只看扩展名或名字；对于边界文件记明确理由。
- 文件名过滤不是内容安全检查；生成前检查实际候选内容中的秘密和个人信息，不输出这些值到审查报告。
- 发现敏感信息暂停相关导出。仅在授权、可恢复的源码版本或明确副本中脱敏，标明变化和对应版本；不要直接在Word上遮掩后冒充未修改源码。登记例外交存/封存另见[依据与登记边界](evidence-and-compliance.md)。
- 不偷偷跳过读取/编码失败的文件。遇到不支持的文本或控制字符，定位并处理来源问题；不能删掉字符继续生成“全量”声明。

## 排序要反映这个系统

1. 先按[系统质量审查](source-quality-review.md)确认实际主链路；选择最能引导读者理解的真实入口或公开业务接口。
2. 沿调用/数据/状态链安排核心实现及必要支撑，最后或就近放置相关配置、测试；不强制所有系统“UI→控制器→模型”同一种顺序，也不平均分配前后端篇幅。
3. 编排单位是**完整文件**；文件内部的imports、声明、注释、类/函数与配置顺序都不动，不拼凑半个函数，不让所有imports跨文件合并到首页。
4. 生成器默认提供入口/普通源码/配置/测试的保守排序；复杂系统需要有依据的业务顺序时用-SourceOrder精确列出**全部自动候选文件**，每个一次。遗漏或额外路径会报错，不借排序缩小范围。
5. 用户明确限定范围，或已核定需要覆盖扫描器未识别的自有文件时，使用-SourceFiles，记录授权、清单与排除依据；它代表“指定范围完整输出”，不能自动标成整个系统全部源码。两个范围/顺序参数不混用。

例子只用于选择思路：算法库可从公开推理/处理接口进入；事件监测可按接入→状态处理→反馈；业务系统可按权限→规则→持久化；桌面应用可从操作入口追到服务与结果展示。最终以实际代码依赖为准，没有该结构就不套。

## 保真与文件边界

- 保留空白行、行尾空格、注释、缩进及声明；仅约定换行符适配、编码BOM处理和tab可视化展开。记录原始字节哈希与导出文本哈希，不把二者混称原文件指纹。
- 一次文件终止换行不是额外空白逻辑行；真实空白尾行仍属源码。排版补白单独计数，只能为空，不参与源码指纹。
- 没有文件标题的既有版式继续保留；用外部清单的RelativePath、StartLine/EndLine、逐文件指纹追溯边界，不向正文添加“文件xxx”分隔行。逻辑行映射不是PDF页内物理行号，自动折行后必须按实际文档定位。
- 导出前冻结源码版本；生成后与原文件逐项对照。改变源码、范围或顺序后必须重新扫描、审查和生成，不能复用旧指纹当新版本证明。
