# 生成有项目依据的软著源程序材料

**固定的是版式，不是每个系统的内容和架构。** 从真实系统的场景、实现与证据出发；正常模块化/复用不是缺陷。既不机械输出大段无解释的代码，也不为降低相似数字改坏源码或编造特色。发现实质重复，先分类与核验，必要时在已授权源码中解决。

## 开始时确定边界

- 读[输入要求](references/input-requirements.md)及[既有格式规范](references/formatting-standard.md)，核实项目、名称、版本和交付目的。保留原规范，不凭“更专业”另做封面或更换字体。
- 只有历史DOCX/PDF：可审计可见注释、相似片段和格式，但不能据汇编文档重建真实模块并宣称全量/可运行；要生成新系统正式源码材料需取得真实源码。
- 仅授权排版：源码只读，指出质量缺口，不在Word里补造注释。明确授权注释/代码质量改进或同时开发该系统：在可恢复的真实项目版本中落实并验证，再导出。大重构、新功能和第三方源码外发不因调用本skill自动获授权。
- 默认完整源码、零截取；若要实际登记专用材料，读[法规与工程依据](references/evidence-and-compliance.md)区分交存方式与归档版。每页50个编号行位不自动等于满足登记行数，排版通过也不等于受理通过。

## 先过内容审查，再冻结源码

按[系统特色、注释与重复审查](references/source-quality-review.md)执行，记录可写在已有任务计划/审查结果中，不强制每项目另造一套文档。

1. **辨认系统**：找出实际场景、主要数据/状态链路、决定行为的业务规则或算法约束。每项“特色”关联文件/符号和测试或待验证状态；不套固定创新点数量，不把换名、颜色、权重路径或配置当作算法创新。
2. **检查注释**：重点审查关键模块职责、调用契约、单位/边界、非显然选择与异常/副作用。能确认的才写；直白代码不逐行解释。没有注释比例或每函数字数任务，原有注释并非一律重写。
3. **分类重复**：正常imports/声明、合法公共组件、误收集副本、同一业务知识的重复维护分别处理。各文件必要导入原样保留；不跨文件只留一次、不合成伪单文件。不同路径同内容先标记，不自动删模块。
4. **落实授权内改进**：在源码里补准注释或修正有证据的重复维护，读回变更并做语言检查/相关回归。只有需求没有实现，或核心质量缺口未解决，就明确未完成；不能新增“创新故事”掩盖。如果只完成忠实排版，交付时仅声明这一项。

项目较大或需跨系统比较时，可用scripts/review-source.py辅助；它从冻结清单读取源码、分列Python注释/imports/相同代码窗口，始终输出needs-human-review。非Python、解析失败和注释语义补人工核验；没有查重率或原创判决，不上传代码。用法与局限见[工具参考](references/工具边界与独立核验.md)。

## 完整编排与生成

1. 按[范围与排序规则](references/source-selection-rules.md)核定全部自有源码，排除第三方、生成物与敏感内容。检查自动扫描遗漏/误排除，不把扫描器的结果等同于范围已审完。
2. 先运行scripts/generate-source-code.ps1的-ScanOnly核对清单。按实际业务链排列完整文件；需要专用顺序用-SourceOrder覆盖全部候选，明确限范围才用-SourceFiles并如实标记。不要通过“精选核心代码”缩减默认全量目标。
3. 冻结源码版本。保留原始注释、imports、空行、行尾空格与缩进；只做约定编码/换行/tab打印适配。不增加正文文件标题、功能介绍或分隔说明，以外部清单定位文件边界。
4. 使用相同范围/顺序参数调用scripts/generate-source-code.ps1生成正式文件，保存返回清单和逐文件原始/打印文本指纹；与生成前清单比较，改变内容/顺序后重新审查。读取/编码失败必须解决，不跳过后仍报“全量”。
5. 输出目录有同名文件先核对并备份或换新目录；不覆盖原件。命令与返回字段见[工具参考](references/工具边界与独立核验.md)。

## 格式不变量

以[完整格式规范](references/formatting-standard.md)为唯一版式细则，下列不能因内容优化丢失：

- A4纵向、四边25.4mm；**无独立封面/目录，首页直接从源码开始**，单节，首页/奇偶页不另设页眉页脚。
- 正文微软雅黑8磅、固定13.8磅行高、关闭行高网格；单正文段落、手动换行，不语法高亮。
- Word原生左侧行号：从1起、逐行、每页重启；空白首行也编号1。每页实际可见1—50，末页只补无文字行位，不计为真实源码。
- 页眉：系统名称、版本、“源程序”和动态PAGE / NUMPAGES；统一微软雅黑11磅、常规字重、#666666，底线#A6A6A6。
- 页脚默认居中动态PAGE、微软雅黑8磅；仅确认匹配无页脚样本时用-NoFooterPageNumber，生成与校验同开关。
- 正式文件始终命名为源程序代码.docx与源程序代码.pdf；页数由真实内容和折行决定，不追求60/69页或不同项目必须有不同页数。

## 独立验收与交付

- scripts/validate-output.ps1检查Word布局/页眉页脚和正文元数据自洽；它的通过不等于原文件全量覆盖或PDF逐页通过。
- 按[工具参考](references/工具边界与独立核验.md)对原文件清单、实际DOCX正文与PDF做独立对照。可用scripts/verify-source-export.py核对原文/指纹、DOCX文本和PDF逐页可见行号/页眉页脚/非空白源码；再真实查看首、中、末页及长行/中文等风险页。自动检查未覆盖的视觉或法律事项不写已通过。
- Word非末页必须严格统计50行，末页可能因最终段落标记统计49；只有最终PDF每页实际可见1—50才能确认该版式要求。不同系统的格式应一致，内容应忠实体现各自实现，不为制造差异改变打印规范。
- 报告：实际文件数、源码逻辑行数、补白行位、原始文件/正文指纹和Word/PDF页数；简要交代本系统有依据的特色、注释改动/缺口、重要重复的处置与验证状态。
- 分清内容质量、来源保真、版式验收和登记适用范围；未验证/未完成项明确保留。哈希证明一致性，不证明独创性；不承诺老师或工具的检测分数。
