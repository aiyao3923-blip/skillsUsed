1. 证据优先级

## 1. 证据优先级

按以下顺序确定项目事实：

1. 用户明确确认的登记事实。
2. 已有登记申请表、受让文件等正式材料。
3. 操作说明手册、用户手册和源程序文档封面。
4. 项目配置、依赖清单、构建脚本、数据库结构和源代码。
5. README、设计说明、测试报告和项目截图。
6. 有明确技术证据支持的归纳。

同一字段出现冲突时，列出冲突并请求确认。不得静默选择最方便的值。文件路径仅用于追溯，不得进入登记文字。

只有确认属于当前软件及其版本谱系的既有登记材料，才能进入上述事实证据优先级。其他软件的登记表或截图不属于事实证据。

权利取得方式和权利范围属于法律事实：

- 只有用户确认软件由著作权人独立或合作开发且权利为原始形成时，才填写“原始取得”。
- 存在转让、继承、承受等情形时，应由用户确认是否填写“继受取得”并准备相应证明。
- 只有用户确认申请人拥有软件著作权的全部权利时，才填写“全部权利”。
- 选择“部分权利”可能触发网站后续权项，本 Skill 必须提醒用户继续核对页面。

## 2. 历史样例使用边界

用户提供历史登记表、其他软件截图或旧填报信息时，读取 `historical-style-guide.md`：

- 学习字段信息密度、短句结构、中文分号和单段说明风格。
- 不复制样例中的领域、硬件、工具、依赖、源程序量、功能或技术结论。
- 先删除样例专有名词形成抽象结构，再用当前项目证据重新填写。
- 当前网站字符限制优先于历史样例长度；历史主要功能较短时仍必须扩展为500—1300个真实字符。

## 3. 字符统计规则

- 对文本执行 Unicode NFC 规范化并去除首尾空白，再按 Unicode 字符计数。
- 常规汉字、中文标点、英文字母、数字和普通符号均按一个字符计算。
- 避免表情、生僻扩展字符和不可见控制字符。
- 限字字段使用单段纯文本，不换行，不加入 Markdown 标记。
- 50 字字段以准确、具体为先，通常控制在 35—45 字符以内。
- “软件的主要功能”必须为 500—1300 字符，建议 700—1000 字符。
- 技术特点补充说明不超过 100 字符；其他编程语言不超过 120 字符。

## 4. 字段顺序与填写规范

### 权利取得方式

仅使用“原始取得”或“继受取得”。不得由代码仓库归属、提交记录或开发者身份自动推定。

### 软件全称

使用稳定、正式、可识别的软件名称。与手册封面、源程序文档及已有材料保持一致。名称通常以“软件”“系统”或“平台”等软件属性词结束；除非正式名称本身包含版本，否则不要把版本号重复写进全称。

### 软件简称

只有项目长期、明确使用简称时才填写。没有简称时留空，不填“无”。

### 版本号

保留项目正式写法，例如 `V1.0`。不得为了格式美观擅自改变已确认版本。若不同材料分别出现 `1.0`、`V1.0` 或其他版本，先请求确认。

### 权利范围

仅使用“全部权利”或“部分权利”，必须由用户确认。

### 软件分类

- 应用软件：面向终端用户或业务场景提供具体功能。
- 嵌入式软件：主要运行于设备、控制器、芯片或专用硬件内。
- 中间件：主要为其他软件提供通用服务、通信、数据或运行支撑。
- 操作系统：负责硬件资源管理并为应用提供基础运行平台。

大多数桌面端、Web、移动端和算法业务系统属于“应用软件”。不得仅因使用嵌入式设备数据就选择“嵌入式软件”。

### 开发的硬件环境（不超过50字符）

填写实际开发设备的硬件类别与关键配置，如处理器、内存、显卡和存储。只写有证据或用户确认的配置，不虚构具体型号。使用中文分号分隔同级配置，规范写作 `16 GB内存`、`1 TB固态硬盘`。

### 运行的硬件环境（不超过50字符）

填写软件正常运行所需或实际部署使用的硬件。客户端、服务器和专用设备按真实架构选择重点。实际使用同一设备时可以与开发硬件一致，不为制造差异而虚构配置。

### 开发该软件的操作系统（不超过50字符）

填写开发阶段使用的操作系统及必要版本信息，不混入 IDE、数据库或编程语言。操作系统名称与版本之间保留空格，如 `Windows 10操作系统`。

### 软件开发环境/开发工具（不超过50字符）

优先填写 IDE、编辑器、编译器、SDK 和构建工具，可保留必要版本号。框架和运行依赖原则上放入支持软件字段，除非其确实构成主要开发环境。不要堆砌所有依赖。

### 该软件的运行平台/操作系统（不超过50字符）

填写最终软件运行或部署的操作系统、浏览器平台、移动平台或服务器平台。Web 系统应区分服务器运行环境与用户访问端。

### 软件运行支撑环境/支持软件（不超过50字符）

填写运行时、框架、数据库、Web 服务器、浏览器或关键依赖组件，不重复操作系统内容。使用官方大小写和中文分号，如 `PyTorch；NumPy；Matplotlib`。

### 编程语言

依据源文件扩展名、构建配置和项目结构选择网站已有选项。HTML、XML、SQL 只有实际构成软件源程序时才选择。列表中没有的语言写入“其他编程语言”，不得把框架名称当成编程语言。

### 源程序量

优先采用现有申请材料或经确认的源程序统计。需要扫描项目时：

- 排除 `.git`、依赖目录、虚拟环境、缓存、构建产物和自动生成文件。
- 同时报告物理总行数与非空物理行数。
- 默认建议填写非空物理行数，但必须说明统计口径。
- 不把 PDF、Word、图片、模型权重、数据集、日志和配置锁文件计入源程序量。

### 开发目的（不超过50字符）

说明为什么开发该软件以及要解决的核心问题。使用“面向……提供……，提高/实现……”的单句事实性表达，不写功能清单、宽泛社会价值或市场宣传。

### 面向领域/行业（不超过50字符）

填写直接服务的行业或应用领域，可写一至三个高度相关领域，不罗列泛化行业。

### 软件的主要功能（500—1300字符）

采用单段、直接、事实性的登记语言，按“定位—输入—核心模块—处理过程—结果输出—管理支撑—适用对象”的顺序组织：

1. 用一两句说明软件定位、使用对象和业务目标。
2. 说明用户可导入、录入、采集或管理的数据。
3. 逐项概括真实存在的核心模块、操作入口和处理动作。
4. 说明软件怎样完成分析、计算、检测、生成、检索或业务流转。
5. 说明界面展示、文件导出、报告、统计结果或其他用户可见输出。
6. 仅在项目确实具备时说明账户、权限、历史记录、参数配置、日志等支撑功能。

不得复制手册中的大段安装步骤，不得用同义句反复凑字数，不得编造未实现模块。

### 软件的技术特点

先从网站提供的标签中选择与项目直接相关的类别。标签是分类，不等于技术说明；不要为了显得先进而多选。

补充说明不超过100字符，应概括有源代码或文档证据支持的架构、算法、数据处理、交互、部署或安全特点。优先使用“采用……；支持……；实现……”的事实句式，不把“创新性”“原创性”作为无内容的固定标题，避免绝对性能指标和无法验证的领先性描述。

## 5. 内容生成方法

建立字段证据表后再生成文字：

| 字段 | 首选证据 | 可辅助证据 |
|---|---|---|
| 软件名称、版本 | 正式材料、手册封面 | README、程序标题栏 |
| 开发/运行环境 | 配置、构建和部署文件 | 手册环境章节、用户确认 |
| 编程语言 | 实际源文件、构建配置 | 技术说明 |
| 源程序量 | 已确认统计 | 行数统计脚本 |
| 开发目的、行业 | 项目说明、用户确认 | 功能和使用场景归纳 |
| 主要功能 | 操作手册、真实界面、源码模块 | README、测试材料 |
| 技术特点 | 源码架构、算法与依赖 | 设计说明、部署配置 |

主要功能和技术特点必须贴合当前项目。示例文字只能用于理解结构，不能直接迁移到其他软件。

## 6. 最终检查

- 必填字段均有值，软件简称除外。
- 法律事实和正式名称版本已经用户确认。
- 所有枚举值来自网站允许选项。
- 所有限字字段通过脚本校验。
- 主要功能达到500字符且不超过1300字符。
- 技术特点标签数量合理，补充说明不超过100字符。
- 各环境字段互不混淆，不使用空泛重复表述。
- 不含本机路径、文件名、账号、密钥或个人信息。
- 不含待补充标记、Markdown、换行或宣传性绝对表述。
- 历史样例只影响表达风格，未把其他软件的专有内容带入当前项目。
- 技术名称大小写、硬件容量单位、操作系统版本空格和中文分号使用规范。
- 最终输出说明源程序量统计口径和关键证据来源。
