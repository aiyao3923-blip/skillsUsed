# 软著登记信息

## 依据与边界
- 先检查已有项目材料，不重复索要已经提供的事实。用 [填写规则](references/filling-rules.md) 确定来源优先级、字段用语与法律边界；填结构化草稿前读 [字段规范](references/field-schema.json)。
- 区分当前项目事实与仅供风格参考的历史样本。使用旧表/截图作样式参考时才读 [历史风格指南](references/historical-style-guide.md)；另一软件的功能、行业、环境和数量不能移植过来。
- 将字段映射到源码、文档或主人陈述；开发硬件、运行硬件、开发系统/工具、运行平台与支持软件分别核对，不为显得不同而编造配置。软件名称/版本须与手册、源程序和申请材料一致。
- 权利取得方式、权利范围、官方名称/版本只能依据明确材料或主人确认；集中询问尚未解决的法律事实。已有有效确认直接沿用，不再加一轮固定审批。

## 填写与校验
1. 按字段规范的英文键生成 UTF-8 JSON。`_confirmation` 中的 `rights_acquisition_confirmed`、`rights_scope_confirmed`、`software_name_version_confirmed` 仅在对应事实确已确认时设为 true，不能为通过校验而伪填。
2. 没有可靠源码数量时，使用 `scripts/count_source_lines.py <source-root> --json-output <report.json>`，报告物理行/非空行；默认推荐非空物理行，现有申请明确另一口径时遵循并注明。
3. 使用经本机环境说明核验的文档环境解释器（本机为 myenv13），以 UTF-8 模式运行 `scripts/validate_registration_info.py <draft.json> --strict-final`；修正报错，并审阅非阻塞用语警告。命令和路径按真实工作区展开，不用 base 或裸 PATH 解释器。
4. 文本先做 Unicode NFC 和首尾去空白，再按 Unicode 字符计数。一个汉字、标点、字母、数字或符号各计一字；避开 emoji/补充平面字符导致的门户 UTF-16 差异。字段单段、不含换行。
5. 50/100 字上限不是目标长度；主要功能按字段规范保持 500–1300 字，优先 700–1000 字有事实依据的内容，不灌水。所有枚举、必填和限制以当前字段规范及真实门户要求核对。

## 内容质量
- 无既定简称时留空，不填“无/暂无”。保留正式产品名、语言、框架、数据库和系统的拼写。目的、用户可见功能与实现技术分开写。
- 不写“国内首创/国际领先/完全自主”等无依据断言，不作绝对安全或性能保证。门户字段不含 Markdown、项目路径、源码文件名、凭据、个人数据或内部草稿说明。
- 缺失项可明确列为待确认，但不能输出带“待补充/TODO/TBD/未知”等占位内容的正式登记结果；不能为交付而编造。

## 交付
默认给可直接复制的中文登记字段、有限字段的实际字数/限制、源码统计口径及简短来源/确认说明，不让主人手动检查 JSON。只有 strict-final 成功且事实核对通过才声明“全部通过”；否则列明仍缺的具体事实或修正项。
