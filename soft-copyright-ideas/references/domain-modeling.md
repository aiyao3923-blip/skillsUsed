# 领域建模与架构规划

本文件只在 `full_plan` 模式读取。所有实体、状态、规则和页面名称应引用已确认基线中的术语；推测内容必须标注为方案建议。

## 推导顺序

```text
已确认目标和场景
→ 角色任务
→ 主业务闭环
→ 用例
→ 实体及关系
→ 状态转换
→ 规则和事件
→ 指标
→ 功能能力
→ 架构与数据流
→ 页面和接口
→ 测试与材料落点
```

不要先用通用后台菜单反推领域功能，也不要为凑数量创建实体或模块。

## 角色与任务

每个角色至少写清：触发场景、目标、输入、动作、输出、数据范围和禁止动作。核心任务卡包含：

```text
任务名称、执行角色、触发事件、前置条件、输入、主成功路径、备选路径、异常路径、完成结果、状态变化、消息/日志、验收证据。
```

权限至少分为菜单、操作、数据、字段和状态五层。角色不同但页面和动作完全相同，必须解释原因；否则视为角色建模缺口。

## 主闭环

主闭环必须覆盖：

```text
触发 → 角色 → 输入 → 校验/规则 → 业务处理
→ 状态变化 → 持久化 → 输出 → 通知/日志 → 业务终态
```

根据领域补充退回、撤回、取消、超时、冲突、复核、返工、归档或解除路径。流程不能停在“保存成功”。

## 实体账册

核心实体至少记录：

| 实体 | 业务含义 | 标识字段 | 核心字段 | 关联实体 | 数据来源 | 负责人 | 敏感级别 | 生命周期 |
|---|---|---|---|---|---|---|---|---|

区分主数据、业务交易、过程记录、附件、日志和统计结果；说明一对一、一对多和多对多关系。

## 状态账册

| 对象 | 当前状态 | 动作 | 操作者 | 前置条件 | 下一状态 | 副作用 | 失败提示 |
|---|---|---|---|---|---|---|---|

检查：每个非终态有合法出口，每个状态有进入来源，动作受角色和状态共同限制，UI、枚举、接口和材料使用同一名称。状态转换优先使用显式业务动作接口，不用任意字段更新绕过规则。

## 规则与事件

规则至少考虑格式/必填、唯一性、时间期限、状态前置、权限范围、阈值等级、冲突检测和统计口径。每条规则写出触发条件、判断逻辑、系统动作、优先级、可配置性和用户提示。

事件记录产生时机、事件数据、订阅者、通知方式和审计要求。事件应能解释待办、通知、日志、统计更新、接口调用或自动任务。

## 指标

每个指标记录：

```text
业务定义、计算公式、统计对象、维度、时间范围、数据来源、更新频率、筛选条件、钻取目标、空数据表现。
```

图表不得使用没有明细来源的固定数字。指标与列表或详情的聚合口径必须可互相校验。

## 技术修饰词

对 AI、预测、实时、智能、区块链、数字孪生等词，写清：

```text
输入数据 → 清洗/归一化 → 特征或指标
→ 规则/模型处理 → 结果分级 → 人工确认/处置
→ 反馈和留痕 → 验证方法与降级方案
```

没有数据、机制和验收方法时，将该词标为风险、候选或后续版本，不伪造核心能力。

## 架构和数据流

根据实际范围说明客户端、路由/权限、领域业务、服务/API、持久化、文件、任务通知、日志审计和 Mock/真实接口边界。非功能指标应与项目规模、数据量和部署环境相符，不机械套用高并发或分布式指标。

每条核心流程说明数据来源、校验位置、被创建/更新的实体、状态变化、读取页面、受影响指标和生成的消息/日志。

## 图表按需选择

- 单流程项目：主流程图和关键状态表；
- 多角色审批：增加状态机或时序图；
- 预警/算法：增加数据流、结果分级和处置链；
- 多端系统：增加系统上下文和端间数据边界。
