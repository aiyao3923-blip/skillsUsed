# 输出契约

## 按模式输出

### 题目初诊

1. 原题目和已有版本；
2. 语义和词类拆解；
3. 题目与实现证据的初步缺口；
4. 已有事实、方案建议、未核验项；
5. 一至三个高影响问题和候选答案；
6. 明确当前没有锁定完整系统。

### 场景选择

1. 领域摘要和研究证据；
2. 保守、平衡和扩展（或其他有明显差异的）场景；
3. 每个场景的用户、闭环、对象、数据、依赖、风险和题目匹配度；
4. 推荐及理由；
5. 待用户选择或授权代拟的事项。

### 需求基线

1. 已确认、授权代拟、待确认、未决和冲突状态；
2. 问题—回答—基线项追踪；
3. 基线草案；
4. 影响说明；
5. 明确的确认提示；
6. 未确认前不输出最终详细规划。

### 完整规划

根据适用性输出：

1. 封面和执行摘要；
2. 原始输入、用途、研究证据和需求基线；
3. 题目语义、原型、场景和系统边界；
4. 角色、任务、权限、主/辅助闭环和用例；
5. 实体、关系、状态、规则、事件和指标；
6. 功能地图、模块、系统原理、上下文、架构和数据流；
7. 信息架构、页面清单、用户旅程和核心页面规格；
8. 视觉、可视化、演示数据和接口契约；
9. 实施工作包、依赖、测试和验收；
10. 软著材料一致性、风险、追踪矩阵和参考来源。

不适用的章节说明理由，不用空表伪装完成。

### 审计

1. 审计范围和证据清单；
2. 现状与目标区分；
3. 题目词、需求、功能、页面、代码、测试和材料的追踪结果；
4. 冲突、缺口、风险等级和证据强度；
5. 按优先级排列的修正建议；
6. 未核验事项和下一步。

### 变更影响

1. 变更编号、原因、前后值；
2. 受影响的题目、角色、流程、实体、状态、规则、页面、接口、测试和材料；
3. 局部变更或重大变更判断；
4. 需要重新确认的基线项；
5. 增量修改顺序和回归检查。


## 实施工作包与特殊用途

完整规划的实施部分按依赖而不是日历输出。每个工作包至少包含：

```text
工作包编号、目标、输入/依赖、实施内容、交付物、验收条件、关联功能/页面、风险和退出条件。
```

默认不编造按天工期；只有用户提供人员、范围和截止日期时才估算日程。核心闭环、数据层、权限和接口契约通常先于仪表盘、复杂算法和外部集成。

如果用途是学生展示、评审、资质或招标，单独列出用途约束、原文条款、证明方式和真实可实现边界。不要把“关键词覆盖”当成功能实现，也不要承诺登记或中标结果。
## 语言约束

把“计划实现”“原型展示”“Mock 数据”“当前已实现”“已验证”分开写。不要把设计建议写成客户事实、行业规定或官方要求。

“完成”必须附证据层级：内部材料初评、外部来源核验、机械检查、真实环境验证或端到端验证。不能用页面美观、命令成功或截图存在单独证明业务闭环完成。
