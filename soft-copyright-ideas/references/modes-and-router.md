# 模式路由与状态机

## 路由原则

先判断用户请求的交付物，再判断输入是否足够。题目、方向、招标关键词和简略需求可以启动分析，但不能自动成为完整需求基线。

### 模式判定表

| 模式 | 优先触发词或输入 | 必须完成 | 禁止越界 |
|---|---|---|---|
| `title_triage` | “题目怎么样”“改个题目”“分析这个名称”或只有标题 | 题目规范化、词类识别、覆盖风险、少量问题 | 不锁定完整产品、页面、技术栈 |
| `scenario_selection` | 题目＋用途，场景或主用户不清 | 最小领域研究、2～3 个有差异的场景候选、选择影响 | 不把推荐场景当成用户选择 |
| `baseline` | 用户连续补充需求或要求确认方案 | 合并决定、检查冲突、列出未决项、形成基线草案 | 不在未确认前输出最终详细规划 |
| `full_plan` | 用户明确确认基线，或用户提供的材料明确标注为已确认且用户授权按其执行 | 按确认范围推导完整计划和审计 | 不扩张到未确认的产品能力 |
| `audit` | 提供已有方案、代码、截图、README、说明书或招标文件 | 盘点现状证据、找缺口和不一致 | 不把建议改动伪装成现状事实 |
| `change_impact` | “增加/删除/改成……”且已有基线或计划 | 记录变更、分析影响、区分局部和重大变更 | 不静默沿用受影响旧前提 |

如果用户只要求其中一个局部输出，选择最小模式。例如只要题目候选名称，不进入 `full_plan`。

如果输入本身是工作流规范、Skill 草案或既有计划，而不是待分析的软件题目，使用 `audit` 做规范/覆盖审计；不要把规范文本误当作软件需求并生成另一套系统规划。

## 决策影响测试

对每个未知事项询问：

1. 不知道它是否会改变题目、核心对象、主流程、目标平台、外部依赖、材料声明或交付深度？
2. 不改变时，是否可以标记为方案假设并继续？
3. 改变时，用户是否已经授权代拟？

只有第 1 个问题答案为“会”且第 3 个问题没有授权时，才把事项列为阻塞问题。其他事项可作为明确标记的假设，不要为了形式反复提问。

## 状态迁移

```text
收到输入
  → 识别模式
  → 盘点证据
  → 题目初诊/最小研究
  → 提问或输出候选
  → 吸收用户回答
  → 更新决策与冲突
  → [若需要] 基线草案
  → [完整规划时] 用户明确确认基线
  → 推导/审计/变更分析
  → 追踪审计
  → 输出结果或交接
```

提出一轮问题后停止，等待真实回答。用户一次性提供多轮信息时可以批量吸收并跳过已回答项；不能用内部推演代替用户回答。

## 快速路径

以下情况可以缩短流程：

- 用户只要题目初诊：直接给题目分析、风险和最多三个关键问题；
- 用户已经提供完整且相互一致的需求：提取为基线草案，请用户一次确认后继续；
- 用户明确授权“由你决定所有剩余方案”：仍需列出代拟的具体事项、理由和影响，并让用户确认汇总结果；
- 用户只要求审计现状：以现状证据为主，不要求重新完成全部访谈。

快速路径不取消“事实、建议、现状和待确认”区分。

## 结束条件

每次响应必须满足当前模式的一个明确结束条件：

- 需要用户决定：输出最小问题集并等待；
- 可以交付当前模式：输出结果、证据状态和下一步；
- 被外部核验阻塞：说明未核验事实及替代路径；
- 完整规划：通过基线门并完成质量审计，或明确列出未通过项。
