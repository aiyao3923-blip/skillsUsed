# 题目分析方法

## 题目词分类

先把原始题目拆成词类，不要把每个词都当作业务功能：

| 词类 | 作用 | 常见后续证据 |
|---|---|---|
| 领域词 | 确定业务边界和术语 | 领域事实、词典、角色 |
| 核心对象 | 确定管理或处理对象 | 实体、列表、详情、生命周期 |
| 业务动作 | 确定用户和系统动作 | 用例、按钮、状态转换、接口 |
| 业务结果 | 确定完成条件 | 终态、指标、报告、验收 |
| 技术修饰词 | 可能要求特殊机制 | 数据、算法、规则、验证 |
| 软件形态词 | 表示产品形式 | 平台、导航、材料命名 |
| 版本词 | 贯穿交付物 | UI、代码、文档和申请信息 |
| 宣传/模糊词 | 需要澄清或降级 | 可验证定义或风险标记 |

## 规范化检查

检查以下事项，但不要在用户确认前把候选名称写成最终名称：

- 原题目、候选题目和版本号分别保留；
- 识别题目是否固定、允许优化或由用户授权代拟；
- 判断词语是否过宽、重复堆叠或将业务结果误写成技术实现；
- 检查题目与目标平台、实现深度和实际资产是否冲突；
- 对可能涉及侵权、误导或登记风险的名称，只报告风险，不作法律判断。

## 题目词到证据

每个核心实词都要完成以下映射：

```text
词义 → 领域事实或用户意图 → 必要业务能力
→ 实体/状态/规则 → 页面/API → 测试和材料落点
```

例如“故障预警”不能只对应一个仪表盘卡片，至少要说明数据来源、指标或阈值、事件生成、确认/处置、解除和留痕机制。若只有“随机展示一个红色数字”，应标记为不可作为真实核心能力的风险。

## 候选题目输出

题目允许调整时，优先给出差异明确的候选，而不是只换同义词：

| 候选 | 保留核心词 | 替换/删除词 | 对应能力 | 需要的真实证据 | 适用用途 | 风险 |
|---|---|---|---|---|---|---|
| 保守表达 |  |  |  |  |  |  |
| 平衡表达 |  |  |  |  |  |  |
| 扩展表达 |  |  |  |  |  |  |

候选表达必须说明：

- 题目覆盖了什么；
- 题目没有声称什么；
- 对功能范围、页面、数据和材料的影响；
- 哪些事项仍需用户选择或确认。

## 题目初诊的最小输出

用户只提供题目时，输出：

1. 原题目和版本（如有）；
2. 一至三句通俗解释；
3. 词类拆解和明显风险；
4. 当前证据与未决项；
5. 一至三个最关键的问题，每题给出互斥选项、推荐和影响；
6. 明确说明不会在用户回答前锁定完整系统方案。

不要为了展示能力提前生成最终角色矩阵、页面清单、数据库表或技术栈。
