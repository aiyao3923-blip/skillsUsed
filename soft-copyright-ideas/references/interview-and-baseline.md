# 访谈与需求基线

## 访谈目标

访谈不是让用户填写一张产品需求问卷，而是把会改变目标方案的未知事项转化为用户可以判断的业务选择。只询问当前模式所需、且不能从已有输入可靠得到的决定。

## 按交付物确定必填项

| 交付物 | 最少需要的决定 |
|---|---|
| 题目初诊 | 原题目、版本（如有）、是否允许改名、用户希望得到的分析类型 |
| 场景选择 | 题目、用途、目标使用环境、主要用户或核心问题 |
| 需求基线 | 软件身份、用途、场景、用户、核心对象、主流程、范围、平台、实现深度、数据、外部依赖和交付物 |
| 完整规划 | 已确认的基线，以及与架构、权限、视觉、验收和材料有关的条件项 |
| 既有方案审计 | 要审计的资产、审计目标、现状与目标是否允许不同 |
| 变更影响 | 当前基线/计划版本、变更内容、变更原因和是否接受范围变化 |

申请主体、权属、隐私、招标和监管事项按用途或题目条件触发；仅做题目初诊时不要机械追问全部法律或部署信息。

## 问题排序

每轮优先问对下列对象影响最大的未决事项：

1. 题目是否固定以及交付用途；
2. 使用环境、主要角色和核心对象；
3. 主流程起点、终点和 V1.0 边界；
4. 平台、实现深度和数据来源；
5. 外部依赖、技术修饰词、权限和非功能；
6. 视觉、指标和交付材料。

一次通常提出一至三个相互关联的问题。问题过多时按影响排序分批，不把整张矩阵一次倾倒给用户。

## 好问题的格式

```text
已核验背景：<只写与当前决定有关的事实，并标记来源或不确定性>
需要决定：<一个明确的业务决定>

选项一：<结果导向的通俗描述>
选项二：<结果导向的通俗描述>
选项三：<必要时提供>

推荐：<推荐及理由，不等于确认>
影响：<会改变哪些范围、页面、数据、技术或材料>
```

避免直接问“你需要哪些功能”“要不要 RBAC”“数据库用什么”。应把技术问题翻译为用户可以判断的使用结果。

## 授权代拟

授权必须有范围：

- “技术栈由你决定”只授权技术栈；
- “按最适合学生展示的方式决定”授权与该用途相关的方案选择，但仍要列出选择；
- “所有剩余事项你推荐”可以覆盖剩余方案决定，但不能覆盖用户未授权的权属、真实客户、事实或法律判断。

代拟结果要记录理由、替代方案、影响和状态，不能因为用户说“直接做”就抹掉未说明的高影响决定。

## 回答吸收和冲突

收到回答后：

1. 把用户明确表达转换为决策记录；
2. 标记哪些是用户事实、哪些是授权代拟、哪些仍是建议；
3. 检查题目、用途、平台、角色、流程、数据和外部依赖之间的冲突；
4. 只追问会改变正确目标的缺口；
5. 回显“已确认 / 推荐待确认 / 未决 / 冲突 / 本轮影响”。

典型冲突包括：完全离线但依赖在线服务、只做前端但要求多用户持久化、单用户但要求多级审批、没有数据却要求实时预测。

## 需求基线

基线至少包含：

```text
基线编号与版本：
软件全称、简称、版本和题目调整权限：
使用目的与成功标准：
申请主体和已知权属事实：
目标使用场景、用户和核心问题：
核心对象与主流程起点/终点：
必须实现、明确排除、后续版本：
目标平台、实现深度、部署环境：
数据来源、演示数据、外部系统、硬件和算法要求：
组织、权限、安全、隐私和合规：
视觉、分辨率、指标和交付内容：
授权代拟事项及理由：
不适用事项及理由：
未决事项和冲突：
```

同时保留问题到基线项的追踪关系，避免基线出现无法回溯的结论。

## 基线确认门

完整规划前必须满足：

- 当前模式所需的高影响决定已经确认、明确排除、不适用，或已授权代拟并确认；
- 没有未解决冲突和阻塞项；
- 用户已经看到完整基线及其影响；
- 用户明确表示按该基线继续规划。

推荐确认语：

```text
以上是后续规划的需求基线。角色、流程、数据、架构和页面都会从它推导。
请确认按此基线继续；如需修改，请指出具体条目。
```

单个问题的回答不能自动解释为整份基线已确认。
