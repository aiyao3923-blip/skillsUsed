# 软著思路

## 适用范围

本 Skill 处理从“软件题目、方向或简略需求”到“可追溯的系统原理与可视化界面实现计划”的分析工作，包括：

- 题目规范化、关键词拆解和候选题目分析；
- 领域预研究、业务原型识别和应用场景选择；
- 自适应需求澄清、冲突检查和需求基线；
- 角色、用例、闭环、实体、状态、规则、指标、架构和页面推导；
- 演示数据、接口、实施工作包、验收和软著材料一致性审计；
- 对已有计划、代码、截图、README 或招标条款进行覆盖和一致性检查。

不要把本 Skill 用作单独填写软著登记字段、生成操作说明书、生成源程序鉴别材料或承诺登记/招标结果；这些任务应交接给相应的专用 Skill。

## 核心工作方式

1. **先识别请求模式**：根据用户要的是题目初诊、场景选择、需求基线、完整规划、既有方案审计还是变更影响分析，选择相应路径。不要对所有请求执行完整流程。
2. **盘点输入证据**：区分用户明确提供的目标要求、工作区中观察到的现状、外部来源事实、已有文档主张和模型建议。冲突不能静默消解。
3. **建立轻量状态**：维护决策账本、证据账本、追踪关系和未决冲突。需要跨轮次或交付文件时，使用 `references/decision-and-evidence-schema.md` 中的结构；可从 `references/state-template.json` 复制初始状态。
4. **做最小充分研究**：只研究影响当前决定的领域事实；完整规划时再扩展研究面。动态或官方要求必须给出来源、访问日期和适用范围。
5. **自适应提问**：每次只问当前最影响正确性的少量问题。用户已主动提供的信息直接吸收；用户明确授权的代拟决定只在授权范围内使用。
6. **按模式输出**：题目初诊可以在未有完整基线时输出；详细系统、页面和架构规划必须在适用的需求基线确认后进行。
7. **证据化推导**：从已确认的场景和目标推导闭环、领域模型、功能、页面、接口和测试，不从页面数量反推功能。
8. **完成审计**：检查题目关键词覆盖、状态与规则闭合、指标口径、权限、数据一致性、外部依赖、材料一致性和未声明事实。

## 模式路由

详细判定规则见 `references/modes-and-router.md`。默认模式如下：

| 模式 | 适用输入 | 主要结果 |
|---|---|---|
| `title_triage` 题目初诊 | 只有题目、方向或关键词 | 规范化题目、语义槽位、风险点、关键问题 |
| `scenario_selection` 场景选择 | 题目已有但用途/场景不清 | 领域摘要、候选场景、推荐与取舍 |
| `baseline` 需求基线 | 用户正在补充或确认需求 | 决策状态、冲突清单、基线草案和确认提示 |
| `full_plan` 完整规划 | 基线已确认 | 系统原理、模型、架构、页面、接口、实施和验收计划 |
| `audit` 既有方案审计 | 存在代码、截图、README、计划或招标文件 | 证据盘点、缺口、冲突、追踪审计和修正建议 |
| `change_impact` 变更影响 | 已有基线或计划后提出修改 | 变更前后、影响范围、增量修改和重新确认项 |

若用户没有说明模式，依据请求的交付物和输入完整度判断；只有当不同解释会改变输出范围时才追问一个澄清问题。

## 不可违反的领域不变量

- “用户没反对”不是确认；“推荐”不是用户决定；沉默不是授权。
- 用户确认的是目标方案，不等于当前系统已经实现；规划、原型、Mock、已实现和已验证必须分开标注。
- 题目中的核心词必须能追溯到领域证据或用户意图，并进一步落到能力、模型、页面/接口和验收证据；无法落地时提出风险或改题建议。
- 不虚构客户、用户规模、上线状态、真实接口、硬件、AI 效果、权属、开发日期或招标结论。
- “AI、实时、预测、智能、区块链”等技术修饰词必须说明输入、处理机制、输出、验证和降级方式；否则只能标记为待确认或风险。
- 软著部分只报告官方要求的待核验项和材料一致性风险，不作法律结论、不承诺登记成功。
- 题目初诊和场景选择不应输出未经确认的最终角色、页面树、数据表或技术栈；可以输出明确标注的候选示意。
- 低信息输入的首轮响应必须以一至三个关键问题结束并等待用户真实回答；不得在同一响应中模拟答案、跨过等待节点或输出完整规划。
- 完整规划完成前，必须通过适用的需求基线门；若存在未决阻塞、冲突或推荐待确认项，输出当前阻塞和最小下一步，不伪装为完成。

## 证据标记

在重要结论和计划表中优先使用以下标记：

- `[用户确认]`：用户明确表达或选择；
- `[授权代拟]`：用户明确授权模型决定，且已写入并确认基线；
- `[外部事实]`：来自可复核的外部来源；
- `[现状证据]`：来自文件、代码、运行结果或截图的直接观察；
- `[方案建议]`：模型基于证据提出的设计选择；
- `[待确认]`、`[未核验]`、`[冲突]`：尚不能作为最终前提。

## 参考资料加载规则

不要默认读取全部参考资料，只读取当前模式需要的文件：

- 题目初诊：`modes-and-router.md`、`title-analysis.md`；
- 场景选择：再读 `research-protocol.md`、`domain-archetypes.md`；
- 需求基线：再读 `interview-and-baseline.md`、`decision-and-evidence-schema.md`；
- 完整规划：再读 `domain-archetypes.md`、`domain-modeling.md`、`ui-and-data.md`、`output-contracts.md`；
- 审计或交付收口：再读 `quality-audit.md`、`handoffs.md`、`decision-and-evidence-schema.md`；
- 涉及动态登记要求：读取 `official-sources.md`，并执行实时核验，不把参考清单当作当前事实。

## 输出控制

- 先给当前模式的摘要、状态和可执行下一步；大规模表格和页面卡按需展开或作为附录。
- 计划书中区分“目标方案”“现状实现”“待核验外部依赖”和“后续版本”，不要用一套措辞覆盖四者。
- 完整规划使用 `references/output-contracts.md` 的章节契约；不适用的章节说明理由，不静默伪造内容。
- 用户只要求意见、题目优化或审计时，不主动生成源代码、说明书或完整实现。

## 交接与验证

需要登记信息、操作说明书或源程序鉴别材料时，读取 `references/handoffs.md`，输出结构化交接包后交给对应 Skill。需要机械检查状态和追踪关系时，运行：

```text
<目标环境 Python>/python.exe scripts/validate_plan.py <state.json> [plan.md]
```

验证脚本只能证明结构性不变量，不能替代领域判断、官方核验或真实端到端测试。
