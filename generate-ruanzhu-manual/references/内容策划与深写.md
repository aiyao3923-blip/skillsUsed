# 内容策划与深写

新写、整体扩写或需要摆脱模板化时使用。先决定“读者怎样完成工作”，再决定目录；不要先生成八章空架子再往里填句子。

## 1. 用系统画像决定组织主线

用一段简洁说明或已有项目记录回答：

- 谁在什么场景下使用？首次用户、熟练操作者和维护人员分别要解决什么问题？只列真实存在的角色，不为显得完整而虚构管理员/审批员。
- 处理什么业务对象？对象从输入到结果经过哪些真实状态？哪些输入/配置会影响后续动作或输出解释？
- 系统交付形态是什么？免安装网页、桌面工具和部署型服务的准备章节不会相同；系统确实不需要的安装内容可以省略。
- 哪些特征值得多花篇幅：领域约束、参数联动、长任务、质量判读、设备反馈、跨模块交接、特殊导出结构等？哪些只是通用按钮，不值得重复展开？
- 哪些事实来自当前源码/文档，哪些已实操，哪些只见于旧稿或尚未确认？缺失的是写作材料，还是实现本身尚不存在？不要混为一谈。

内部维护一张可追踪的小表即可，允许复用项目现有记录，不强制另建一套报告：

| 用户任务/能力 | 真实入口与事实证据 | 关键条件/结果 | 说明位置与深度 | 操作/截图验证或缺口 |
|---|---|---|---|---|
| 按当前项目填写 | 文件与符号、说明页码、实际界面等仅内部留存 | 能影响操作或判断的事实 | 章节/参考位置 | 已实操、仅源码确认、待确认等 |

同一任务可以跨多个模块，同一模块也可服务多个任务。以实际能力清单反向检查手册，不能只根据自己拟定的目录证明自己“覆盖完整”。

## 2. 统一语义骨架，不统一章数

完整手册需覆盖五个问题：为什么使用/边界是什么；开始前准备什么；如何做事；怎样确认与交付结果；不符合预期时如何恢复或安全结束。它们可以合并、拆分、穿插，不能为凑齐标题而写无用章节。

可按实际系统选组织主线，也可组合：

| 主线 | 适用判断 | 正文组织的可能变化 |
|---|---|---|
| 数据或产物生命周期 | 同一数据连续经过多个处理步骤 | 输入合格性 → 加工任务 → 中间质量检查 → 成果交付；跨模块案例贯穿，而非逐按钮介绍 |
| 用户的业务任务 | 使用者按目标独立调用多项功能 | 以“完成某项工作”为章/节；提供任务入口索引，菜单说明退为辅助 |
| 运行状态/设备反馈 | 操作强依赖当前状态和外部反馈 | 启动前检查、运行中观察、状态切换、异常结束分别说明；演示/仿真与真实设备边界明确 |
| 角色与交接 | 确有不同角色、权限和真实交接动作 | 各角色任务及交接条件形成闭环；公共步骤引用，不复制整套手册 |
| 分析与决策 | 结果需要参数选择和专业判读 | 基础操作与参数选择、结果解释、误判边界分层；必要原理贴近决策而不是独立堆论文 |

“系统概述—准备—操作—结果—故障”的大章骨架可以复用。真正的区别必须发生在业务章的拆合顺序、任务内容、证据或解释方式上。“总结”“致谢”“总体架构”都不是固定必选章。

## 3. 差异化必须有证据，也必须有作用

为本系统选择少量有区分力的“特色锚点”，逐一对应：**真实特征 → 读者要作的选择/可能犯的错 → 采用何种说明 → 如何验证**。不按固定数量考核，也不能只说“智能化、可视化、易用”。

下面是取材方向，不是待生成系统必备功能；未被当前项目证实的能力不得落入正式目录或正文：

- **数据集辅助创作类**：如果确有成对数据、批量裁切/退化或打包功能，可围绕对应关系、尺寸/数量一致性、中间产物检查和后续使用组织；不能未经实现就增加去重、数据划分、断点续作等能力。
- **图像检测/识别类**：如果真实支持多种输入模式或检测参数，可说明输入条件的差异、参数对结果的影响、类别/置信度的含义及人工复核边界；没有标定与单位证据时不能把像素量描述为实际尺寸。
- **融合/科研处理类**：若确有多源输入、配准或评价指标，需要说明输入配对与可比条件、处理后的判断依据；不因系统名称含深度学习就增设训练章节，不把一次观察写成准确率保证。
- **实时监测/跟踪类**：若界面与实现存在相应状态，重点说明输入连接、开始/停止、状态反馈和结果留存；“仿真演示”不等于真实设备控制，不能推测存在失联重连、告警确认或自动处置。

可按需要采用的说明方式：

| 方式 | 何时有用 | 应包含的证据 | 不应怎样使用 |
|---|---|---|---|
| 端到端案例 | 多个功能共同产出一个成果 | 同一真实输入、关键配置、中间状态、最终结果和检查动作 | 将快速上手原文再复制一次，或只更换案例名称 |
| 参数决策表 | 参数含义或联动会影响用户选择 | 单位、支持范围/默认值来源、适用条件、调整影响与观察方法 | 编造推荐值；把示例值说成默认值或最优值 |
| 输入合格性清单 | 错误输入导致失败或误导结果 | 支持条件、识别方法、实际错误反馈和可用替代操作 | 罗列与软件无关的通用文件安全常识 |
| 状态流转/故障树 | 结果依赖先后顺序或异常分支 | 已确认的状态/提示、转入条件、恢复后的检查 | 凭常识发明“暂停/回滚/续传” |
| 结果对照/字段解读 | 成功提示并不足以判断成果可用 | 结果字段、单位、输入关联、已知局限、保存后复核 | 只有美观的大图，或仅写“效果良好” |

目录定稿前做一次“替名检查”：将产品名遮住，是否仍能从任务、数据对象、约束、决策与结果中辨认系统？如果不能，检查的是实质取材，不是要求每本手册发明不同修辞。

## 4. 任务有深浅，信息有分层

### 核心任务

复杂、多分支或出错代价高的任务应使读者找到以下信息，但可组织成自然段、步骤、图表或局部参考，不强制八格卡片或固定三级标题：

1. **目标与终点**：完成后得到什么，哪种状态表示结束；谁可执行。
2. **前置条件**：进入时的状态、所需输入及其限制；不是重复安装章。
3. **入口与动作**：真实界面名称或已交付的命令入口、操作次序、提交/确认动作。对于真实命令行/配置型功能，必须给足用户可执行的公开文件名、参数和相对位置；先区分公开接口与开发机内部路径，不凭空改写成不存在的按钮。
4. **关键选择**：需要用户判断的配置，单位与默认/示例/建议值分清。
5. **可观察反馈**：动作改变了什么；等待/完成/失败如何区分，时长未知就不编等待秒数。
6. **结果判读**：看哪些内容，为什么能判断结果有效；系统成功运行不等于业务结果正确。
7. **已知分支**：会影响这项任务的失败现象、判别依据、已支持的恢复方式及复验点。未证实的错误仅在内部作为待测项。
8. **后续去向**：保存、导出、交接、进入下一任务或安全结束；按真实支持的方式验证持久化，不臆造系统内回读功能。

### 简单任务和共用内容

单按钮切换、导航和已解释过的步骤不必扩成大节。交代入口、动作和必要反馈即可，引用准确的公共节号或图表。公共说明引用必须能在最终目录中定位，不能写“见前文”却没有对应内容。

新手路径提供一次可获得成果的连续练习；熟练用户路径解决具体工作；参数/字段参考便于查阅；原理解释只补决策所需。借鉴 Diátaxis 的分层思想，不把四种文档需求机械变成四章。

### 从“描述按钮”改成“指导工作”

薄弱写法：“选择图像，设置参数，点击检测，查看并导出结果。”

需要补的不是同义改写，而是当前项目的事实：图像入口/支持条件是什么；哪项参数在当前场景需要选择；点击后出现什么状态；如何判别无检测结果与执行失败；结果字段怎样关联输入；导出后检查什么。把这些问题用真实值与真实操作回答，才会增加有价值的篇幅。尚无证据时把问题记入缺口，不能用想象填答案。

## 5. 先写可执行章节，再扩展全书

先挑一个最有代表性的核心任务写完整，试排验证真实内容密度和截图可读性。验收其动作、结果、分支及后续去向后，再将同样的信息质量标准用于其他任务；不要复制它的小标题和段落来批量填充。

跨章节跟踪同一业务对象、术语、配置和结果，避免“上一章导出的东西下一章无法使用”。图注说明任务状态/观察重点，正文解释读图结论；图不是无上下文的装饰，也不是替代操作文字的凭据。
